Agentic Loop Engineering

A single model call is a function you can review before it runs. A loop is a program that decides its own control flow — and then takes actions in your systems. This is what you actually own once you put a model inside a while: the tools, the budget, the exit doors, the context, and the blast radius.

01 Why a Loop Changes Everything

The first agent I put into production did something I still think about. Asked to find why a nightly job had started failing, it read the logs, formed a sensible hypothesis, checked the wrong config file, found nothing, re-read the same logs, formed the same hypothesis, checked the same wrong file — and did that eleven more times before the budget ran out. Every individual step was reasonable. The sequence was insane.

That's the shape of the problem. Putting a model in a loop doesn't just make it more capable; it changes the failure modes entirely. A single call can be wrong. A loop can be wrong persistently, expensively, and with side effects.

Start with the arithmetic, because it explains most of what follows. Suppose each step in your loop is 95% reliable — a good number, better than most tool-using steps manage on messy real-world input. Ten steps in sequence, all of which must be right:

99%

90%

Two things fall out of that table, and they set the agenda for this entire article. First, per-step reliability compounds brutally — the difference between 95% and 99% per step is the difference between a coin flip and something you'd ship. Second, and more importantly: a loop that can notice and recover from a bad step beats a loop with better steps. Recovery breaks the multiplication. That is the whole game.

💡 What this article assumes

That you've written prompts that work and now want to put one inside a loop that calls tools and changes things. If you haven't read it, the companion piece on prompt engineering covers the single-call foundations — structured output and injection defence especially, both of which get harder here.

02 A Prompt Is a Call, a Loop Is a Program

The mental model from single-call work was: the model is a pure function, and your prompt is the argument. That still holds, but it's no longer the interesting part. In a loop, something stranger is true: the model has become your control flow.

You wrote no if statements. You didn't decide that step three would be a database query rather than a web search. You didn't write the retry. The model chose all of it, at runtime, and it will choose differently tomorrow on the same input.

So what do you actually own? Five things — and everything in this article is about one of them.

🧰

The Tools

The instruction set. The model can only do what you gave it a verb for.

🧠

The State

What's in context each turn, what gets compacted, what gets forgotten.

⛔

The Exit Doors

Budgets and termination conditions. Enforced in code, never in prose.

🔐

The Permissions

What a successful run — or a hijacked one — is physically able to do.

🔭

The Trace

Whether you can reconstruct why it did what it did, after the fact.

The useful reframe: you are not writing the program. You are designing the machine the program runs on. You specify the instruction set, the memory model, the fuel, and the halting conditions. Someone else — something else — writes the program, fresh, every run.

One practical consequence worth internalising early: your debugging question changes. It used to be "why is this output wrong?" It is now "why did it take this path?" You cannot answer that question from the final output. You can only answer it from a trace, which is why section 9 is not the optional one it looks like.

03 The Anatomy of an Agent Loop

The loop itself is almost insultingly simple. Here it is, complete, with nothing that matters in it:

Pseudocode var state = initialContext(task); while (true) { var response = model.call(state, tools); if (response.isFinal()) return response.result(); var results = execute(response.toolCalls()); state = state.append(response, results); }

Eight lines, and every one of them is a lie by omission. There's no budget, so it runs forever. There's no error handling, so one 503 kills the run. state.append grows without bound. There's no progress check, so it can ping-pong between two tools until your bill arrives. And execute will happily run whatever the model asked for.

The real loop is the same eight lines wrapped in guards. Here is what a production version actually looks like in shape — the annotations are the article:

Java · the shape that survives public RunResult run(Task task, Budget budget) { var state = initialContext(task); var progress = new ProgressTracker(); // §5 — no-progress detection for (int turn = 0; turn < budget.maxTurns(); turn++) { budget.assertNotExhausted(); // §5 — tokens, cost, wall clock state = contextPolicy.fit(state); // §6 — compaction happens HERE var response = model.call(state, tools); // §7 — transport retries inside trace.recordTurn(turn, state, response); // §9 — before anything can throw if (response.calledFinish()) { return RunResult.completed(response.result(), trace); } var results = executor.execute( // §11 — gates live in here, response.toolCalls(), task.permissions()); // not in the prompt if (progress.isStuck(response.toolCalls(), results)) { return RunResult.stalled(state, trace); // §5 — break the ping-pong } state = state.append(response, results); } return RunResult.budgetExhausted(state, trace); // §5 — partial work, not an exception }

04 Tools Are an API Contract

If you want one lever that improves an agent more than anything else, it is not the system prompt. It is the tools. I have watched teams spend a week rewording instructions to stop an agent misbehaving, when renaming two tools and fixing an error message would have done it in an afternoon.

The reason is simple once you see it: a tool definition is a prompt. The name, the description, the parameter names, the parameter descriptions — all of it goes into the model's context on every single turn. A vague tool description isn't a documentation problem. It's a prompt problem that you're paying for repeatedly.

Design for the agent, not for your service

The most common mistake is wrapping an existing REST API one-endpoint-to-one-tool. Your API was designed for a programmer who has read the docs, holds the domain model in their head, and can compose six calls to get one answer. The agent has none of that and pays context for every option you expose.

Expose the operations an agent needs, not the surface you happen to have. Five well-named tools beat forty faithful ones, every time.

Make errors instructive

Every tool error lands in the model's context and becomes the input to its next decision. That makes error messages the highest-leverage strings in the entire system, and most of them are wasted.

Format that works: what failed · why · what to do differently. The third clause is the one everybody omits and the only one that changes the next turn.

Control what a tool returns

Tool output is not a response to your program. It is text you are injecting into the model's context, permanently, for the rest of the run. A tool that dumps 40,000 tokens of JSON hasn't returned data; it has poisoned every subsequent turn with cost, latency, and noise.

  • Cap and paginate. Return the first N with a cursor and a total count, not everything.
  • Return the answer, not the payload. If the agent always computes the same summary from a blob, compute it in the tool.
  • Return handles for big things. Write the 40k-token file to storage, return the path plus a 200-token summary. The agent can read the parts it needs.
  • Truncate loudly. "…showing 20 of 4,312 results, use cursor=abc for more" is information. Silent truncation is a bug the model will confidently reason past.

Two properties worth engineering for

Idempotent where possible. Retries happen — from your transport layer, from the model repeating itself, from a resumed run. A tool that's safe to call twice removes an entire category of incident.

Destructive operations should be awkward. Not update(entity, fields) where one field happens to be deleted=true, but a separate, narrowly-named archive_order that the model has to deliberately choose — and that your executor can gate on. Ambiguous verbs get invoked by accident.

Consistent wrong-tool selection is almost never a reasoning failure. It's a specification failure, and there are four usual culprits — check them in this order:

  • Overlapping descriptions. If searchOrders and findOrders both say "find orders matching criteria", you have not given the model a decision procedure — you've given it a coin. Every description should contain an explicit "use this when… use X instead when…" clause. That single sentence fixes more wrong-tool problems than anything else.
  • The name lies. Models weight the name heavily. getUser that actually performs a fuzzy search across three systems will get called in situations where a fuzzy search is wrong. Name it what it does.
  • Too many tools. Past roughly a couple of dozen, selection accuracy degrades noticeably and the schemas start crowding out actual context. If you're above that, either merge related operations behind one tool with a mode parameter, or split the agent so each sub-agent sees only its own subset.
  • The right tool doesn't exist. The model picks the nearest available verb, because there is no "none of these" option. When you see persistent misuse of one tool, the finding is usually that the task needs a tool you haven't written.

A cheap diagnostic: take twenty real traces, extract just the first tool call from each, and check them by hand. Wrong-tool problems show up in the first call far more often than in the fifth, and the pattern is usually obvious once the calls are side by side without the surrounding narrative.

05 Termination — The Hard Part

Here's the thing nobody warns you about: knowing when to stop is harder than knowing what to do. A model that is 90% good at choosing the next action can be nearly 0% good at recognising that there is no useful next action — because "I should stop now" competes against a very strong prior that a helpful assistant keeps helping.

Four legitimate exits, and only four

Every run must leave through one of these doors. If your loop has a path that doesn't, it has an infinite path.

  1. Completed — the model called the finish tool with a result.
  2. Budget exhausted — turns, tokens, wall clock, or money hit a ceiling.
  3. Stalled — your progress detector concluded it's going in circles.
  4. Escalated — the agent hit something requiring a human, and said so.
Diagram 2 — Exit Doors and the Runaway Shapes They Catch
Runaways are not exotic. They're three shapes, and each has a cheap mechanical guard.

Make "done" a structured event

Do not ask the model to "stop when the task is complete" in prose and then try to detect completion by inspecting its output. Give it a finish tool with required parameters, and treat calling that tool as the only way to succeed.

Java · the finish tool does real work @Tool(name = "finish", description = """ Call this when the task is complete. This is the ONLY way to finish. You must provide evidence: which tool results support your answer. If you cannot provide evidence, the task is not complete — keep working or call escalate() instead. """) public void finish( @Param(description = "The answer, addressing the original task directly") String result, @Param(description = "Turn numbers whose tool results support this answer") List<Integer> evidenceTurns, @Param(description = "Anything you could not verify, or empty") List<String> caveats) { }

The evidenceTurns parameter is doing something sneaky and valuable. Requiring the model to point at the observations backing its answer makes the "declared success without doing the work" failure much harder to reach — and when it does happen, you can detect it automatically, because you can check whether those turns exist and whether they actually ran the tools claimed.

⚠ Budgets belong in code

"Use at most 10 tool calls" in a system prompt is a suggestion, not a limit. The model cannot reliably count its own turns, and by turn 15 that instruction is buried a long way up the context. Every budget — turns, tokens, wall clock, currency — must be enforced by the caller, checked at the top of every iteration, and hit hard.

And when a budget is hit: return partial work with the reason, not an exception. A run that says "here's what I established in 20 turns, here's what I was about to check next" is useful. A stack trace is not.

06 Context Across Turns

In a single call, context engineering is about choosing what to include. In a loop it becomes something harder, because the context is no longer yours alone — the agent appends to it every turn, and it never appends less.

Turn 1 is a tidy 2,000 tokens. Turn 20, after nineteen tool results have landed, is 80,000. Three things degrade simultaneously and they reinforce each other: cost per turn rises, latency per turn rises, and the signal-to-noise ratio falls exactly as the task gets more complex. The agent gets slower and dumber at the same time, which is why long runs so often feel like they lose the plot near the end. They do.

Diagram 3 — Four Ways to Stop Context Eating the Run
Compaction is lossy by definition. The skill is choosing what it's allowed to lose.

Re-pin the goal every turn

This is the cheapest high-value trick in the article and almost nobody does it. By turn 20, the original task sits tens of thousands of tokens upstream — precisely the "lost in the middle" region where instruction adherence is weakest. Meanwhile the most recent thing in context is a tool result about a config file, which is not what you asked for.

So re-append it. A short block at the end of the context on every turn:

Appended after the latest observation, every turn --- CURRENT TASK (unchanged since turn 0) --- Find why the nightly reconciliation job started failing on 6 Aug and report the root cause with evidence. Constraints: read-only access. Do not restart the job. Turn 14 of 25. Tokens used: 41k of 120k. Already tried and ruled out: - config drift in reconciler.yml (turn 3, identical to 5 Aug) - upstream feed delay (turn 7, feed landed 02:11, on time) - schema change in ledger table (turn 11, no migrations since 1 Aug)

Three things are happening there. The goal is fresh. The budget is visible, which measurably reduces dithering. And the tried-and-failed ledger is the single most effective anti-looping device I've deployed — most ping-pong behaviour is just an agent that has forgotten it already went down that road.

Compact at checkpoints, not continuously

It's tempting to trim a little every turn. Don't. Every edit to earlier context invalidates the prompt cache from that point on, and in a loop the cache is carrying most of your cost — see section 10. Let context grow append-only, then compact in one deliberate step when you cross a threshold. You pay one cache miss instead of twenty.

07 Error Recovery & Retry Semantics

Recovery is where reliability actually comes from — remember the compounding arithmetic from section 1. A loop that recovers from a bad step doesn't multiply that step's failure into the run.

The core distinction, and getting it wrong is the most common architectural mistake I see in agent code: there are two kinds of error, and they belong to different layers.

Transport errors Semantic errors
Examples Timeout, 503, connection reset, rate limit Bad arguments, not found, permission denied, validation failed
Whose problem Your infrastructure The model's decision
Who handles it Your code, silently The model, on the next turn
Does the model see it? No — retry with backoff, then fail the run Yes — as an instructive message
Failure to separate Model "reasons about" a 503 and invents a workaround Your code swallows a bad-argument error, agent never learns

Surfacing a transport error to the model is genuinely harmful. It will try to be helpful about it — switching tools, inventing a fallback, concluding the data doesn't exist — when the correct behaviour was to wait 400ms and call the same thing again. Conversely, swallowing a semantic error and returning an empty result teaches the agent that the thing it asked for isn't there, which sends it down a completely wrong branch with total confidence.

Java · the split, made explicit public ToolResult execute(ToolCall call, Permissions perms) { try { // Transport failures retry in here and never reach the model. return ToolResult.ok(retrying(() -> dispatch(call, perms))); } catch (ToolException e) { // Semantic: the model asked for something wrong. It must see this, // phrased so the next turn can do something different. §4 return ToolResult.error(e.guidanceForModel()); } catch (TransportException e) { // Retries already exhausted. This is not the model's problem to // solve — fail the run cleanly rather than let it improvise. throw new RunFailedException("tool transport failed: " + call.name(), e); } }

Cap the semantic retries too

Feeding an error back is only useful if the model learns from it. When the same semantic error occurs three times consecutively, it isn't learning — either the error message isn't actionable, or the thing the agent wants genuinely cannot be done. Both are conclusions, and both should end the run through exit door 3 or 4 rather than burning the rest of the budget.

💡 The error message is the fix

When you find an agent stuck in a retry loop, the instinct is to add a rule to the system prompt. Resist it. Go and read the actual error string the tool returned. Nine times in ten it says something like "Error: invalid request", and rewriting it to name the problem and the remedy fixes the behaviour with no prompt change at all — and fixes it for every future agent that touches that tool.

08 Multi-Agent: When It Helps, When It Doesn't

Let me be blunt, because this is where a lot of effort gets wasted: most multi-agent systems are worse than one well-equipped agent, and they're worse for a reason that sounds boring until it bites you. Splitting work across agents means splitting context, and context is where the agent's understanding lives.

When you hand a subtask to another agent, you are choosing to forget everything the parent knew that didn't fit in the handoff message. You've introduced a serialisation boundary and, with it, an entire distributed-systems failure surface — except the protocol is English and the nodes are non-deterministic.

So the question is never "does this task have three parts?" Tasks always have parts. The question is: am I buying context isolation, parallelism, or a permission boundary? If the answer is none of those three, use one agent.

Diagram 4 — Three Topologies and What Each One Buys
The middle topology earns its keep. The right-hand one is usually one agent wearing three hats.

The three legitimate reasons

  • Context isolation. The strongest reason by far. A subtask needs to read 100,000 tokens of search results to produce a 200-token conclusion. Run it in a sub-agent with its own window; the parent receives only the conclusion. You have bought the parent 99,800 tokens of headroom for the price of one handoff.
  • Parallelism. Genuinely independent subtasks with no shared evolving state — check these six services, summarise these ten documents. Wall-clock time drops by roughly the fan-out. The word doing the work is independent: if worker B needs anything worker A discovered, this isn't parallelism, it's a pipeline with extra steps.
  • Permission boundaries. A read-only researcher and a narrowly write-capable executor. This is a real security win: the agent processing untrusted web content has no write tools, so a successful injection there can't do anything. Section 11 leans on this.
⚠ What the handoff costs

A sub-agent result is a summary written by a system that couldn't ask a clarifying question. The parent gets a confident paragraph and has no way to tell how much was inferred. Mitigate it by making sub-agent results structured rather than prose — findings, confidence, what it could not determine — and by giving the parent a way to ask for the raw material if it needs to.

09 Observability for Loops

You cannot debug what you cannot replay, and with agents you cannot replay from the output — the output is one paragraph at the end of a thirty-step decision tree that will never be reproduced exactly. The trace is the artefact. Build it first, not after the first incident.

Diagram 5 — What a Run Trace Has to Capture
Token counts and cache-hit rates per turn are not vanity metrics; they're how you find the run that quietly cost forty times the others.

The minimum you'll wish you had logged

  • Per run: task, model and version, which exit door it left through, total turns, tokens, cost, wall clock, final result.
  • Per turn: turn index, input and output token counts, cache hit rate, latency, the tool calls with their arguments, and the finish reason.
  • Per tool call: name, arguments, outcome, result size in tokens, duration, and whether it was gated or auto-approved.

Truncate large payloads in the span itself but store the full version behind a pointer. You will need the full version roughly once a month, and on that day nothing else will do.

The artefact that actually gets used

Metrics tell you a run went wrong. Only a rendered transcript — the whole run, top to bottom, prompt then call then result then call, readable like a conversation — tells you why. Build a page that renders one. You will read hundreds of them, and every hour spent making that view pleasant pays back within a week.

Sampled production runs are your eval set

Store a small random sample of full production runs — even 0.1% — plus every run that ended in an exit door other than "completed". That corpus becomes the evaluation set for the agent, and unlike a hand-written one it is made of things that actually happened.

One important difference from single-call evaluation: for agents you score the trajectory, not just the answer. Did it pick the right first tool? How many turns? Did it recover from the error or spiral? Two runs can produce the same correct answer and only one of them is a system you want.

10 Cost & Latency Blowups

Here is the single most under-appreciated fact about agent loops, and the reason so many pilots come in wildly over budget: a 20-turn run does not cost 20× a single call. It costs roughly 200×.

The mechanism is simple once stated. The entire context is re-sent on every turn. If context grows roughly linearly — turn 1 sends 1 unit, turn 2 sends 2, turn n sends n — then total input across the run is the sum of the series, which is n(n+1)/2. Quadratic. Twenty turns of a linearly growing context sends about 210 turn-one-equivalents of input, not 20.

Two consequences follow immediately. First, measure per run, never per call — a dashboard of average cost-per-model-call will look completely healthy while your agent product loses money on every ticket. Second, anything that slows context growth pays back quadratically, which is what makes section 6 an economic argument as much as a quality one.

Prompt caching is worth more in a loop than anywhere else

This is the redeeming detail, and it's genuinely elegant. In an append-only loop, every turn's prompt is the previous turn's entire prompt plus a bit more. That means the cacheable prefix is almost the whole request, and it grows along with the conversation. Loops are close to the ideal case for prompt caching — but only if you leave the earlier turns alone.

The tension with section 6 is real and resolves cleanly: grow append-only, compact rarely and deliberately, and put the volatile "turn 14 of 25" block at the end where it costs you nothing.

Latency is a sum, so buy back turns

Turns are strictly serial — turn n+1 can't start until the tools from turn n return. Total latency is the sum, and users feel every second of it. The levers, in rough order of payoff:

  • Parallel tool calls within a turn. If the model requests three independent lookups, execute them concurrently. This is close to free and most implementations don't do it.
  • Fewer, richer tools. Every tool that answers a question in one call instead of three removes two full round trips of model latency, not just tool latency. This is the real payoff of section 4.
  • Right-size the model per turn. Much of a run is mechanical — deciding to read the next file, extracting a field. A smaller, faster model handles those well; escalate to the large one for planning and final synthesis. Your trace data tells you which turns are which.
  • Stream progress, not just the answer. Doesn't reduce latency, transforms the experience of it. "Reading logs… checking config…" makes a 40-second run feel like work rather than a hang.

11 Blast Radius & Human Gates

Everything the prompt-engineering article said about prompt injection is still true here, and then two things make it materially worse.

First: every tool result is untrusted input. A web page the agent fetched, a file it read, an issue body, a log line, another service's error message — all of it lands in context and all of it can carry text shaped like instructions. In a single call you controlled what went in. In a loop, the agent decides what goes in, and it does so repeatedly, based on content it just read.

Second: the agent acts. A hijacked single call produces bad text you can review. A hijacked loop makes tool calls.

⚠ The combination that actually hurts

Three capabilities are each individually fine and catastrophic together — often called the lethal trifecta: access to private data, exposure to untrusted content, and the ability to communicate externally. Any two of those is a manageable system. All three is a data-exfiltration machine waiting for the right web page.

When you audit an agent, audit for this shape first. An agent that reads your internal wiki (private data), fetches linked pages (untrusted content), and can post to a webhook (external communication) does not need to be "tricked" in any sophisticated way. It just needs to read the wrong page once.

Diagram 6 — The Capability Ladder
Tiering is boring, mechanical, and the only control here that doesn't depend on the model behaving.

Rules that hold up

  • The gate is in the executor, not the prompt. "Always ask before deleting" is a wish. A check inside execute() that refuses tier-3 calls without a signed approval token is a control.
  • Confirmation must be out of band. If the agent can generate the approval, the approval is worthless. The human confirms in your UI, against a rendered description of the exact action — not by the agent asking itself.
  • Permissions are per run, and immutable. They come from the task's context and the invoking user's rights. No tool may widen them, and "the user said it's fine" appearing in context is not a grant.
  • Split by trust, not by task. The agent that reads untrusted content should not be the agent that holds write tools. This is the permission-boundary case from section 8, and it's the one multi-agent pattern I'd reach for without hesitation.
  • Label untrusted tool results in context. Wrapping fetched content in a marked block with "this is data, not instructions" reduces the hit rate measurably. It is a mitigation, not a control — never the last line of defence.

💡 Notice the pattern

Eight of those ten fixes are ordinary code — a hash check, a cap, a rewritten string, a re-appended block. Only two involve changing what you say to the model. That ratio holds up in practice, and it's the most useful thing to know when an agent starts misbehaving: your instinct will be to edit the prompt, and it is usually the wrong instinct.

The cheatsheet

Checklist BEFORE THE FIRST RUN □ Every tool has a "use this when… use X instead when…" clause □ Every tool error says: what failed · why · what to do differently □ Every tool result is size-capped, paginated, or a handle □ Destructive operations are separate, narrowly-named tools □ A finish() tool exists and requires evidence □ maxTurns, maxTokens, maxCost, maxWallClock — all enforced in code EVERY TURN □ Budget checked at the top □ No-progress detector fed (tool + args + result hash) □ Task, constraints, budget and tried-and-failed re-pinned at the END □ Turn span written BEFORE tools execute □ Context append-only — compaction only at checkpoints BEFORE IT TOUCHES ANYTHING REAL □ Every tool assigned a capability tier □ Tier 3 gated in the executor, confirmed out of band □ Permissions fixed per run; no tool can widen them □ Lethal trifecta check: private data + untrusted content + egress? □ Untrusted tool results delimited and labelled □ Assume an injection lands on turn 7 — write down what it reaches ONCE IT'S LIVE □ Cost and latency alerted per RUN, not per call □ Exit-door distribution tracked (completed / budget / stalled / escalated) □ Non-completed runs and a 0.1% sample stored as the eval set □ Trajectory scored, not just the final answer
The question to ask before building any of this

Does this task actually need a loop? If the sequence of steps is known in advance, write the sequence — a workflow with a model call at three fixed points is cheaper, faster, testable, and debuggable, and it cannot spin. Agents earn their complexity when the path genuinely can't be known until you're partway down it. That's a real category, and it's smaller than the enthusiasm suggests.

14 Summary

Five things, if you keep nothing else.

  • Recovery beats accuracy. Per-step reliability compounds, so the loop that notices and corrects a bad step beats the loop with slightly better steps.
  • Tools are the real lever. Names, descriptions, error strings and result sizes move agent behaviour further than prompt wording, and they fix it for every future agent too.
  • Termination is code. Four exit doors, all enforced by the caller. A prompt cannot count its own turns or hold a budget.
  • Context is a managed resource. It grows every turn, costs quadratically, and dilutes the goal. Re-pin the task at the end, compact at checkpoints, never lose the tried-and-failed ledger.
  • Design for the injection that succeeds. Tier your capabilities and gate them in the executor, so a hijacked run is boring rather than expensive.

The honest summary of the whole discipline: putting a model in a loop hands it your control flow, and almost everything in this article is about taking back the parts you should never have given away — the budget, the exits, the permissions, and the record of what happened. The model gets to choose the path. You still own the map, the fuel, and the walls.
