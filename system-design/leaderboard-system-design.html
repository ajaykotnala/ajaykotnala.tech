Designing a Gaming Leaderboard at Scale:
A System Design Deep Dive

It's 10:45 PM IST on the last night of the season. Lakhs of players are squeezing in one more match, and every win has to move them up the table within a second — never lost, never counted twice. Let's build the leaderboard that survives that night, from Redis sorted sets and fair tie-breaks to idempotent writes and sharding for IPL-final traffic.

01Understanding the Problem

Picture GullyStars, a fictional mobile cricket game that's taken off across India. Two players face off in a quick three-over match. A win earns 3 points, a tied match earns 1 point each. Every calendar month is a season, and when it ends, the top of the table walks away with exclusive jersey skins, coins, and the "Season Champion" badge.

The leaderboard is the second most-opened screen in the app, right after the match itself. Players finish a match on the metro home, and the first thing they check is whether they climbed. We're talking about 1 crore daily active players, 3 crore in a month, each playing around 8 matches a day. And the traffic is anything but flat — it piles up between 8 and 11 PM IST, and spikes again on IPL match nights and on the last evening of every season.

On a whiteboard, this looks like SELECT … ORDER BY points DESC LIMIT 10. Three things turn it into a real design problem: ranking crores of players in real time, counting every win exactly once when servers retry, and ranking ties fairly when rewards are on the line.

💡 Interview Tip

Before drawing anything, ask two questions: "How should ties be ranked?" and "Does every player need an exact rank, or only the top N?" Those two answers decide your data structure far more than the traffic numbers do.

02Defining Requirements

Functional Requirements

Here's what the leaderboard has to do:

  • Record match results — reported by game servers: +3 for a win, +1 each for a tie
  • Top 10 of the current season, visible to everyone
  • My rank and points — even when I'm sitting at rank 12,40,000
  • Players around me — the 5 players just above and 5 just below
  • State leaderboards — "Top 10 in Maharashtra" (bonus)
  • Monthly seasons — a fresh table at 00:00 IST on the 1st, with past seasons readable

Non-Functional Requirements

And these are the constraints that make it interesting:

Back-of-the-Envelope

Let's turn the Indian evening into numbers. Matches are 1v1, so 1 crore players × 8 matches ÷ 2 gives us 4 crore matches a day, and every match produces one score update for the winner.

Quantity How Result
Average score writes 4 Cr ÷ 86,400 s ~460/s
Evening peak 35% of matches between 8–11 PM IST: 1.4 Cr ÷ 10,800 s ~1,300/s
Spike nights IPL final, season's last night: ~3× evening peak ~4,000/s → design for 5,000/s
Leaderboard views ~5 per player per day, same evening shape ~5,000/s on spike nights
Ranking memory 3 Cr players × ~110 bytes per sorted-set entry ~3.5 GB per season
Match records 4 Cr/day × ~120 bytes ~5 GB/day

Two things jump out. The whole season's ranking fits in a few GB of memory, and 5,000 writes a second is small for an in-memory store. The hard parts of this system are correctness and spikes, not raw volume.

03Core Entities & Data Model

Four nouns carry the whole design. Getting them straight early saves a lot of back-and-forth later.

👤

Player

Someone who plays matches. Has a display name, avatar and home state, like MH or KA.

🏏

Match Result

The outcome of one match, identified by a unique match_id issued by the game server.

📅

Season

One calendar month in IST, like 2026-10. Points reset when a new season starts.

🏆

Standing

A player's points in one season, plus when they reached that total. This is what gets ranked.

The key decision here: PostgreSQL is the source of truth, and Redis is the ranking engine. Every point lives durably in Postgres first. Redis holds a sorted copy that answers rank questions in microseconds, and can be rebuilt from Postgres whenever it needs to be.

Schema -- PostgreSQL: the source of truth CREATE TABLE season_standings ( season_id TEXT, -- '2026-10' player_id TEXT, points INT NOT NULL, reached_at TIMESTAMPTZ, -- when the player reached this total state_code CHAR(2), banned BOOLEAN DEFAULT false, PRIMARY KEY (season_id, player_id) ); CREATE TABLE match_results ( match_id TEXT PRIMARY KEY, -- the idempotency key season_id TEXT, result JSONB, -- players and outcomes ended_at TIMESTAMPTZ ); -- partitioned by day, archived after 30 days CREATE TABLE score_outbox ( id BIGSERIAL, season_id TEXT, player_id TEXT, points INT, reached_at TIMESTAMPTZ, state_code CHAR(2) ); # Redis: the ranking engine lb:2026-10 sorted set member = player_id, score = encoded points lb:2026-10:MH sorted set same, one per state player:{id} hash name, avatar (profile cache)

04The API Surface

Three endpoints cover the whole product: one for game servers to report results, two for players to read the table.

PUT /internal/matches/{matchId}/result

Reports a finished match. Only game servers can call it — it lives on the internal network behind mTLS, and the public gateway has no route to it. Players never report their own scores.

Request Body { "players": [ { "id": "p_48213", "outcome": "win" }, { "id": "p_90177", "outcome": "loss" } ], "ended_at": "2026-10-14T21:31:07+05:30" }
Design Decision

Why PUT with the match ID in the path, instead of POST /scores? Because PUT is idempotent by contract. A game server that times out can send the exact same request again, and the server records the result once. We'll see in the deep dive why that one choice matters so much.

GET /leaderboards/{season}/top?limit=10&state=MH

The top of the table for a season. Leave out state for the all-India leaderboard.

GET /leaderboards/{season}/me?around=5

The caller's rank, points, and the players around them. The player ID comes from the auth token, never from the URL, so nobody can look up someone else's neighbourhood by guessing IDs.

Response { "season": "2026-10", "me": { "rank": 1240000, "points": 96, "name": "Priya" }, "around": [ { "rank": 1239996, "points": 97, "name": "Karthik" }, … { "rank": 1240000, "points": 96, "name": "Priya" }, … ], "as_of": "2026-10-14T21:31:08+05:30" }

05High-Level Architecture

The system splits cleanly into two paths that meet at Redis. The write path is built for correctness: every result goes through Postgres and a durable log before it touches the ranking. The read path is built for speed: players only ever hit Redis replicas and a small cache.

Diagram 1 — High-Level System Architecture

Writes flow along the top: game server, Postgres, Kafka, then Redis. Reads flow along the bottom and never touch Postgres on the hot path.

Walking Through a Win

  1. Priya wins a match. The game server, which is the only authority on who won, calls PUT /internal/matches/m_7Q2x/result.
  2. The score service writes the match, Priya's new season total, and an outbox row in one Postgres transaction.
  3. Change data capture (Debezium) streams the outbox row into the Kafka topic score-events, keyed by player ID.
  4. The rank updater consumes the event and writes Priya's new total into Redis — the all-India set and her state's set.
  5. Priya opens the leaderboard. The leaderboard service asks a Redis replica for her rank and neighbours, adds names from the profile cache, and responds in a few milliseconds.

Why Redis Sorted Sets?

A Redis sorted set keeps members ordered by score at all times, using a hash table for direct lookups and a skip list for ordered traversal. Here's how it compares with asking Postgres directly:

Question PostgreSQL Redis Sorted Set
Top 10 Fast with an index on points ZRANGE … REV, O(log N)
My rank at 12,40,000 COUNT(*) over 12 lakh index entries, per request ZCOUNT / ZREVRANK, O(log N)
5 above, 5 below A rank query, then an OFFSET scan ZRANGE by position, O(log N + 11)
5,000 updates/s Row update + index churn on a hot table In-memory, O(log N) each
Durability ● Durable ○ Needs a source of truth behind it
⚠️ Watch Out

Redis is fast because it lives in memory, and that's exactly why it must not be the only copy of the points. Treat it as a derived view you can throw away and rebuild. Postgres owns the truth.

06Deep Dive: Never Count a Win Twice

The most common way to build a leaderboard is to add points as they come in: ZINCRBY lb:2026-10 3 p_48213. It's simple, fast, and quietly wrong. Here's a scenario that happens every single night at this scale.

Diagram 2 — How a Retry Double-Counts a Win

The first update succeeded, but its reply was lost. The retry is indistinguishable from a new win, so the points are added again.

Retries aren't a corner case you can ignore. Game servers retry on timeouts, Kafka redelivers after a consumer restart, and deploys interrupt requests halfway. At 4 crore matches a day, even a 0.01% retry rate means 4,000 double-counted wins every day, and on the season's last night some of them decide who gets rewards.

How Do We Fix This?

We need two guarantees, and they come from two separate ideas:

Idea 1: Deduplicate on the Match ID

+

Every match gets a unique match_id from the game server, and match_results.match_id is a primary key. The score service inserts the match and updates the season total in the same transaction. If the match is already there, the insert fails, the transaction does nothing, and the service simply replies "already recorded".

The same transaction writes an outbox row. Debezium reads committed outbox rows from the Postgres write-ahead log and publishes them to Kafka. This is the transactional outbox pattern: the database commit and the event can never disagree, because the event is part of the commit.

SQL BEGIN; INSERT INTO match_results (match_id, season_id, result, ended_at) VALUES ('m_7Q2x', '2026-10', '{…}', '2026-10-14 21:31:07+05:30'); -- duplicate match_id → unique violation → ROLLBACK, reply "already recorded" INSERT INTO season_standings (season_id, player_id, points, reached_at, state_code) VALUES ('2026-10', 'p_48213', 3, '2026-10-14 21:31:07+05:30', 'MH') ON CONFLICT (season_id, player_id) DO UPDATE SET points = season_standings.points + 3, reached_at = EXCLUDED.reached_at RETURNING points, reached_at; -- 96, 21:31:07 INSERT INTO score_outbox (season_id, player_id, points, reached_at, state_code) VALUES ('2026-10', 'p_48213', 96, '2026-10-14 21:31:07+05:30', 'MH'); COMMIT;

Idea 2: Send Totals, Not Increments

+

Deduplication protects Postgres, but Kafka is at-least-once. If the rank updater crashes after writing to Redis but before committing its offset, the same event comes back. An increment would double-count right there.

So the event carries Priya's new total (96), not "+3", and the updater writes it with ZADD … GT. The GT flag only ever raises a score. Replaying the event writes 96 again, which changes nothing. An older event that arrives late carries a lower total, which GT ignores. Points only go up within a season, so this is always safe. (GT needs Redis 6.2 or later.)

Redis # safe to run once, twice, or out of order ZADD lb:2026-10 GT 405646820 p_48213 ZADD lb:2026-10:MH GT 405646820 p_48213

That strange-looking score, 405646820, isn't 96. It's 96 points with a tie-breaker packed inside it — which brings us to the next deep dive.

Latency Budget

Postgres commit ~10 ms, Debezium to Kafka 100–500 ms, consume and ZADD ~10 ms: comfortably under a second. Want it snappier? Let the score service also run the same ZADD … GT right after its commit. The Kafka path still delivers the guaranteed copy, and GT makes the second write harmless.

07Deep Dive: Ties and Fair Ranking

With 3 points per win, ties aren't rare — they're everywhere. Around rank 12 lakh, thousands of players share the same total. So we need two separate answers:

  • What rank do tied players see? The same one. Two players on 1,251 points are both rank 2, and the next player is rank 4. This is called standard competition ranking.
  • Who's listed first? Whoever reached the total first. That decides who's above the cut when rewards stop at position 100, and it's easy to explain to a player.
Rank Player Points Reached at (IST)
1 Arjun 1,254 13 Oct, 10:02 PM
2 Sneha 1,251 14 Oct, 8:15 PM
2 Rohit 1,251 14 Oct, 9:40 PM
4 Kavya 1,248 12 Oct, 11:20 PM

Redis can't do either of these on its own. It orders equal scores by member name, so Rohit and Sneha would be ordered alphabetically by player ID, and ZREVRANK would give them different ranks. The fix is to pack the tie-breaker into the score itself.

Diagram 3 — Packing a Tie-Breaker into the Score

Points take the high bits, so they always dominate. The low bits hold how early in the season the total was reached, so earlier wins ties.

Formula score = points × 2²² + (2²² − 1 − seconds_since_season_start)

Why 22 bits? A 31-day season has 26,78,400 seconds, which fits under 2²² (41,94,304). Points get the remaining 31 bits, so totals up to about 200 crore stay exact inside Redis's 53-bit precision — no player is getting anywhere near that.

In the example, Priya reached 96 points at 9:31:07 PM IST on 14 October, which is 1,200,667 seconds after the season started at midnight IST on 1 October.

The Four Leaderboard Queries

Need Redis Cost
Top 10 ZRANGE lb:2026-10 0 9 REV WITHSCORES O(log N + 10)
My points ZSCORE → 405646820 ÷ 2²², rounded down → 96 O(1)
My shared rank ZCOUNT lb:2026-10 406847488 +inf → 1239999, so rank 12,40,000 O(log N)
5 above, 5 below ZREVRANK → 1240002, then ZRANGE lb:2026-10 1239997 1240007 REV O(log N + 11)

The shared rank is simply "how many players have at least one more point than me, plus one". The lowest possible score for 97 points is 97 × 2²² = 406,847,488, so one ZCOUNT from there to infinity answers it. ZREVRANK gives Priya's position in the list (three players reached 96 before her), which is what the neighbour window needs.

💡 Interview Tip

Interviewers love this moment. Most candidates reach for ZREVRANK and stop. Saying "rank and position are different things once ties exist" — and showing how one packed score answers both — is a clear senior signal.

08Deep Dive: Surviving IPL-Final Night

Our numbers say one Redis node is plenty: ~3.5 GB of data and 5,000 writes a second, when a single node handles well over a lakh simple operations per second. So today's setup is deliberately boring: one primary and two replicas spread across availability zones in the Mumbai region. Writes go to the primary, reads go to the replicas.

The Read Spike Is Easier Than It Looks

On the season's last night, lakhs of players refresh the top 10 again and again. But the top 10 is the same for everyone. Each leaderboard-service pod caches the finished response for 1 second, so 5,000 requests a second turn into roughly one Redis query per pod per second. For a live view, a single publisher reads the top 10 every second and pushes it over Server-Sent Events only when it changed.

When One Node Isn't Enough

Suppose GullyStars goes global and grows 50×. Now we're past what one node can take, and the sorted set has to be split across shards.

Daily Players Peak Writes Ranking Memory Setup
1 Cr (today) ~5,000/s ~3.5 GB 1 primary + 2 replicas
10 Cr ~50,000/s ~35 GB Bigger node, more read replicas
50 Cr (global) ~2,50,000/s ~175 GB 16 shards, each a primary + replica

There are two natural ways to split a leaderboard, and a monthly reset makes the choice between them very clear.

Diagram 4 — Splitting the Leaderboard on the 1st of the Month

Line thickness shows write volume. On the 1st of the month everyone has close to zero points, so a score-range split sends nearly every write to one shard.

Option A: Split by Score Range

+

Each shard owns a band of points. Reads are lovely: the top 10 lives entirely on the highest shard, and a player's rank is their rank inside their own shard plus the size of every shard above it (ZCARD is O(1)).

Writes are the problem. At 00:00 IST on the 1st, every player starts at zero, so the lowest band takes nearly every write for days. The band boundaries have to keep moving as scores grow through the month. And a player crossing a boundary must be removed from one shard and added to another, with no transaction spanning the two.

Option B: Split by Player Hash (Recommended)

+

Each player lives on shard hash(player_id) % 16 for the whole season. Writes are spread evenly from the very first minute, and players never move.

The cost moves to reads. The top 10 means asking each shard for its own top 10 and merging 16 × 10 = 160 rows — cheap, and cached for a second anyway. A shared rank means one ZCOUNT per shard, run in parallel, then summed: a few milliseconds at 16 shards. That trade is well worth even writes on the busiest night of the month.

State Leaderboards Come Almost Free

"Top 10 in Karnataka" is just another sorted set, lb:2026-10:KA. The rank updater writes each event twice: once to the all-India set and once to the player's state set. The biggest state set is a fraction of the national one, so it never needs sharding, and every query from the previous deep dive works on it unchanged.

Beyond Exact Ranks

If exact ranks for hundreds of crores of players ever become too expensive, keep exact ranks for the top 1 lakh and show everyone else a percentile, like "Top 8% in India", computed from a score histogram refreshed every minute. Players care about the top of the table and their own progress, not whether they're 1,42,31,007th or 1,42,31,008th.

09Deep Dive: Season Rollover & Recovery

Midnight IST on the 1st

Season IDs follow IST, not UTC. A season is defined by when a match ended, not when its event was processed, so a match ending at 11:59:58 PM on 31 October counts for October even if Kafka delivers it a minute later.

  • No reset job. The first November result creates lb:2026-11. October's set simply stops receiving writes.
  • Grace window. Results for October are accepted until 00:10 IST, covering matches that were mid-over at midnight. After that the season is frozen.
  • Final standings. A job pages through ZRANGE 10,000 players at a time and writes the final table to Postgres. The rewards job reads from there, and past seasons are served from there too.
  • Cleanup. EXPIRE lb:2026-10 a week after the freeze.

When Things Break

Failure What Players See Recovery
Redis primary dies Rank updates pause for a few seconds A replica is promoted automatically. The updater resumes from its last Kafka offset, and replayed events are harmless thanks to GT.
All Redis copies lost Last cached top 10, marked "updating" Rebuild from season_standings: scan the season and pipeline ZADD in batches of 1,000. 3 crore rows take a few minutes.
Kafka or Debezium lags Leaderboard runs behind; nothing is lost Alert when consumer lag passes 5 seconds. The direct write after commit keeps most updates live.
Postgres and Redis drift A few wrong totals A nightly reconciler compares season_standings with ZSCORE and rewrites any that differ.
Mumbai region outage Read-only leaderboard for a few minutes Fail over to Hyderabad, which runs a Postgres replica and a Kafka mirror. Redis is rebuilt there from Postgres.
⚠️ Cheaters Ruin Leaderboards

Only game servers can write scores, and the score service checks that the match exists, the winner actually played in it, and the match_id hasn't been scored before. A nightly job flags outliers, like more matches in an hour than is physically possible. Banning a player sets banned in Postgres and removes them with ZREM, and rebuilds skip them.

10Final Architecture & Interview Bar

Here's everything in one place. Notice how few moving parts there are: one durable store, one log, one ranking engine, and a handful of stateless services.

Component Technology Rationale
API Gateway Kong / AWS API Gateway Auth, rate limiting; no route to internal score APIs
Score Service Stateless service Validates results, dedupes by match_id
Source of Truth PostgreSQL Season totals, match log, transactional outbox
Event Log Debezium + Kafka Durable, replayable, keyed by player
Rank Updater Kafka consumer group Writes totals with ZADD … GT to national and state sets
Ranking Engine Redis sorted sets (Mumbai) O(log N) rank, top-N and neighbours
Leaderboard Service Stateless service 1-second top-10 cache, shared ranks, live updates over SSE
Profile Cache Redis hashes Names and avatars without touching Postgres
Season Job Scheduled worker Freeze at 00:10 IST, snapshot final table, hand off to rewards

💡 Final Thought

A leaderboard looks like a sorting problem, but it's really a correctness problem wearing a sorting costume. Redis makes ranking easy. The real engineering is making sure every point in it was earned exactly once, that ties resolve the same way every time, and that the whole thing can be rebuilt from the truth in minutes — especially at 10:45 PM on the last night of the season.
