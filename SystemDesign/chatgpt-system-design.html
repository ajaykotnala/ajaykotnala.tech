Designing ChatGPT at Scale:
800 Million Users, One Token at a Time

Every system design you have practised assumes requests are cheap and stateless. This one is neither. A single ChatGPT reply burns more compute than ten thousand ordinary API calls, holds gigabytes of live state, and must stream back word by word. Let's build it — starting from what actually happens inside the model.

01Understanding the Problem

On the surface ChatGPT is the simplest product in this entire series. There is one text box. You type into it, and text comes back. There is no seat map, no geo-spatial index, no matching engine, no payment settlement. A junior engineer could sketch the UI in an afternoon.

And yet it is the hardest system in the series, because it breaks the one assumption every other design in your toolkit is built on: that a request is cheap.

Every system you have designed until now — Tinder, BookMyShow, a ride-hailing app — is fundamentally I/O-bound. The server receives a request, reads or writes some rows, serialises JSON, and returns. The CPU is mostly idle. Requests are stateless, so any machine can serve any request, and you scale by adding boxes behind a load balancer.

ChatGPT inverts every one of those properties:

  • It is compute-bound, not I/O-bound. A single response can consume several GPU-seconds on hardware that costs tens of thousands of dollars per card.
  • It is stateful mid-request. Generating a reply builds up gigabytes of intermediate tensors that must live in GPU memory until the last word is emitted.
  • It is not one request, it is hundreds. A 400-word answer is 400 sequential forward passes through the model, each depending on the output of the last.
  • The response streams. The connection stays open for 10–30 seconds, not 50ms.
  • Capacity is physically scarce. You cannot autoscale your way out of a GPU shortage. There is a global supply constraint, and it is measured in months of lead time.

That last point is what makes this an interesting interview question rather than a trivia quiz. In every other design, the bottleneck is something you built badly and could fix. Here, the bottleneck is the hardware itself, and the entire architecture exists to squeeze more useful work out of a fixed, expensive, oversubscribed pool of accelerators.

💡 Interview Tip

The trap in this question is spending twenty minutes on conversation storage and CRUD APIs — the part you already know how to build — and running out of time before you reach inference serving. Storage is perhaps 5% of the difficulty here. Say so out loud early: "The database side of this is conventional; I'd like to spend most of our time on the inference path, because that's where the cost and the latency live." Interviewers almost always agree, and you have just framed the entire conversation around the interesting half.

02Defining Requirements

Functional Requirements

Scope tightly. These are the features that define the product:

  • Send a message and receive a streamed reply — tokens appear progressively, not as one blob at the end
  • Multi-turn conversation — the model sees the prior turns, so context must be reassembled on every request
  • Persistent history — conversations survive across sessions and devices
  • Stop and regenerate — the user can abort mid-stream or ask for another attempt
  • Model selection — a fast cheap model and a slow expensive one, with different capacity pools behind them

Explicitly out of scope, and worth naming so the interviewer knows you chose rather than forgot: training and fine-tuning, image generation, voice, code execution sandboxes, and the retrieval/tool-calling stack. Each is a system design question of its own.

Non-Functional Requirements

The latency requirements here are unusual and worth stating precisely, because "p99 latency" is almost meaningless for a streaming response. There are two separate numbers that matter, and they are governed by completely different parts of the system:

  • TTFT — Time To First Token. How long from pressing Enter until the first word appears. Target < 500ms p95. This is what users perceive as "responsiveness," and it is dominated by queueing plus one expensive pass over the prompt.
  • ITL — Inter-Token Latency. The gap between successive words once streaming has begun. Target < 50ms, which yields roughly 20+ tokens/second — comfortably faster than reading speed. This is what users perceive as "fluency," and it is dominated by memory bandwidth.

A system with a 300ms TTFT and a 200ms ITL feels broken and stuttering. A system with a 2s TTFT and a 30ms ITL feels slow to start but smooth. They are different failure modes with different fixes, and collapsing them into one "latency" number is the single most common mistake candidates make here.

The Arithmetic That Shapes Everything

Do this math out loud in an interview. It takes ninety seconds and it determines every architectural decision that follows.

Capacity Estimation · 800M DAU REQUEST VOLUME 800M users × 4 conversations/day × 5 turns = 16B messages / day 16e9 ÷ 86,400s = ~185,000 messages / sec (average) peak factor ~3× = ~555,000 messages / sec (peak) TOKEN VOLUME (the number that actually matters) avg prompt (system + history + new turn) = ~1,500 tokens avg output = ~400 tokens prefill: 16e9 × 1,500 ÷ 86,400 = ~278M input tokens / sec decode: 16e9 × 400 ÷ 86,400 = ~74M output tokens / sec GPU FLEET (assume 8×H100 node ≈ 15K output tok/s with continuous batching) 74M ÷ 15,000 = ~4,900 nodes (average) × 3 for peak = ~14,800 nodes = ~118,000 GPUs

A hundred thousand accelerators, to serve a text box. At roughly $25–30k per H100-class GPU that is a capital outlay in the billions before a single conversation happens, and it is why the rest of this article is essentially one long exercise in raising GPU utilisation.

Note which term dominates. Prefill processes 278M tokens/sec — nearly four times the decode volume — yet decode sets the fleet size. That asymmetry is the most important fact in the whole design, and section 07 explains why.

⚠️ The Cost Constraint Is a Design Constraint

In a normal system, a 20% efficiency win is a nice-to-have that saves some money. Here, a 20% throughput improvement is worth roughly 3,000 GPUs — hundreds of millions of dollars of hardware you do not have to buy, on a part with a multi-month lead time. This is why techniques that would be absurd micro-optimisations elsewhere (custom attention kernels, cache-aware routing, speculative decoding) are table stakes here. Cost per token is the primary architectural metric, not p99 latency.

03Core Entities & Data Model

The persistent entities are refreshingly boring, and you should say that. The interesting state in this system is ephemeral and lives on a GPU.

👤

User

Identity, subscription tier, rate-limit budget. Tier determines which model pool the request is allowed to reach.

💬

Conversation

An ordered container of messages. Owns a title, a model binding, and a system prompt. The unit of sharing and deletion.

✉️

Message

One turn. Role (user / assistant / system), content, token count, and the model that produced it. Append-only.

🧠

KV Cache Block

The model's working memory for an in-flight conversation. Lives in GPU HBM, measured in gigabytes, gone when the request ends.

🎛️

Model Deployment

A named model version pinned to a pool of GPU nodes, with its own weights, capacity, and cost per token.

📊

Usage Record

Input and output tokens per request. Drives billing, quota enforcement, and capacity planning. Emitted asynchronously.

The Storage Shape

Messages are append-only, always read as a contiguous range within one conversation, and never joined across users. That access pattern points directly at a wide-column store — partition by conversation_id, cluster by seq:

Message Table · partitioned by conversation PRIMARY KEY ((conversation_id), seq) conversation_id uuid -- partition key: all turns co-located seq int -- clustering key: natural ordering role text -- 'user' | 'assistant' | 'system' content text token_count int -- denormalised, avoids re-tokenising to bill model text created_at timestamp -- One partition read returns the whole conversation in order. -- No joins, no scatter-gather, no secondary index needed.

Conversation metadata (title, updated_at, owner) lives in a separate table partitioned by user_id, so the sidebar list is also a single-partition read. Two tables, two access patterns, zero clever indexing. Total volume is large but unremarkable — 16B messages/day at ~1KB each is roughly 16TB/day, which is a solved problem.

💡 The State That Actually Matters

Notice that the KV cache block appears in the entity list but not in the database schema. That is deliberate, and it is the single most important observation in this design. The model's working memory for an active conversation is measured in gigabytes per user, lives in GPU HBM, cannot be written to disk fast enough to be worth persisting, and evaporates the moment the request completes. Every hard problem in this system — routing, batching, admission control, cost — is downstream of managing that ephemeral state. Section 08 is entirely about it.

04The API Surface

The CRUD endpoints are exactly what you would expect. The one that deserves real thought is the completion endpoint, because it is the only streaming call in the system.

POST /v1/conversations

Create an empty conversation. Returns an id the client uses for all subsequent turns.

POST /v1/conversations/{id}/completions

The main event. Appends a user turn and streams back the assistant's reply token by token over Server-Sent Events. Holds the connection open for the full generation.

Request & SSE Response POST /v1/conversations/c_8f2a/completions { "content": "Explain the KV cache", "model": "gpt-fast", "stream": true } --> Content-Type: text/event-stream data: {"delta":"The", "seq":0} data: {"delta":" KV", "seq":1} data: {"delta":" cache","seq":2} ... data: {"finish_reason":"stop","usage":{"in":1487,"out":392}} data: [DONE]
POST /v1/completions/{request_id}/cancel

Abort an in-flight generation. Critical for cost, not just UX — a cancelled request frees a GPU slot and its KV cache immediately.

GET /v1/conversations?limit=20&cursor=…

Cursor-paginated sidebar list for the signed-in user. Ordinary, cacheable, uninteresting — which is the point.

🔌 Why SSE and not WebSockets

The data flow here is strictly one-directional once generation starts: the server pushes tokens, the client just listens. SSE gives you that over plain HTTP — it survives proxies and CDNs, reconnects automatically, needs no special infrastructure, and costs one ordinary HTTP connection. WebSockets buy you bidirectional messaging you do not need, in exchange for stickier connections, more awkward load balancing, and a protocol upgrade that some corporate proxies quietly break. Cancellation is rare enough to be a separate POST rather than a reason to hold a duplex channel open. Choose the weaker protocol when it fits — that reasoning is what the interviewer is listening for.

05High-Level Architecture

Here is the whole system in one picture. The left half is a conventional web application you could build in your sleep. The right half — everything past the scheduler — is where this design lives or dies.

Diagram 1 · Request Path, End to End
Everything left of the dashed line is a normal web app. Everything right of it is a scheduling problem over scarce hardware.

Walking the Path

  1. Gateway authenticates, checks the user's rate-limit budget, and rejects early. Cheap rejection matters enormously when the downstream resource costs dollars per minute.
  2. Conversation service reads the message history for that conversation, applies the context window policy (truncate or summarise older turns), and assembles the final prompt.
  3. Safety filter screens the input. A blocked prompt never reaches a GPU — which is a cost control as much as a policy control.
  4. Inference scheduler is the brain. It queues the request, decides which node should run it (preferring one that already holds a matching prefix in cache), and admits it into a running batch.
  5. GPU fleet runs prefill over the prompt, then loops decode, emitting one token per iteration back through the open SSE connection.
  6. Usage events fire asynchronously to Kafka for billing and capacity planning — never on the synchronous path.

06Deep Dive: Inside the Model

You cannot design this system without knowing what the box labelled "GPU Inference Fleet" is actually doing. Every scheduling decision later in this article is a direct consequence of the mechanics below, so it is worth being precise — not mathematically rigorous, but precise about the shape of the computation.

Step 1 — Tokenization

The model never sees characters. Text is first split into tokens — subword fragments produced by a learned merge table (byte-pair encoding). Common words are single tokens; rare words shatter into pieces.

Tokenization "The KV cache is the bottleneck" ↓ ["The", " KV", " cache", " is", " the", " bott", "leneck"] ↓ [464, 27653, 12940, 318, 262, 10038, 43163] Rule of thumb: 1 token ≈ 4 characters ≈ 0.75 English words Consequence: code, JSON and non-English text cost MORE tokens per character — and you bill per token.

Step 2 — Embedding

Each token id indexes into an embedding table, producing a vector of a few thousand dimensions. A 1,500 token prompt becomes a 1500 × d_model matrix. From here until the very last step, the model is manipulating floating-point matrices — there are no words anywhere inside it.

Step 3 — The Transformer Stack

That matrix passes through a stack of identical blocks — 80 or more in a large model. Each block does two things, and understanding the difference between them explains most of the performance behaviour of the whole system.

Self-attention lets every token look at every previous token and pull in relevant information. Each token projects into three vectors: a query (what am I looking for?), a key (what do I offer?), and a value (what do I actually contribute?). Attention scores each token's query against every key, softmaxes into weights, and takes a weighted sum of the values. This is the step where "it" gets connected to the noun it refers to, forty words back.

The feed-forward network then processes each position independently through a much wider layer — typically 4× the model dimension. This is where most of the parameters live, and in modern mixture-of-experts models it is split into many expert sub-networks with only a couple activated per token. That is how a model can have a trillion parameters but only spend the compute of a much smaller one on each token.

One Transformer Block x = x + Attention(LayerNorm(x)) # mix information ACROSS positions x = x + FeedForward(LayerNorm(x)) # process EACH position independently Attention(x): Q = x @ Wq # what each token is looking for K = x @ Wk # what each token offers V = x @ Wv # what each token contributes scores = softmax( Q @ K.T / sqrt(d) + causal_mask ) output = scores @ V causal_mask ensures position i can only attend to positions <= i. That single constraint is why text generates left-to-right, and why the KV cache works at all.

Step 4 — The Autoregressive Loop

After the final block, a projection maps the last position's vector to a score for every token in the vocabulary. Softmax turns those into probabilities, and a sampler picks one — greedily, or with temperature and top-p controlling how adventurous the choice is.

Then comes the part that defines this entire system: the chosen token is appended to the input, and the whole model runs again. A 400-token answer means 400 sequential forward passes. They cannot be parallelised, because token 200 depends on token 199 having been chosen.

Diagram 2 · Prefill Once, Then Decode 400 Times
One request, two workloads with opposite bottlenecks. Every optimisation later in this article targets the right-hand box.

Why Decode Is So Wasteful

This is the insight that separates a strong answer from a memorised one, so it is worth stating carefully.

To generate one token, the GPU must read every weight in the model from high-bandwidth memory and multiply it against a single vector. For a 70B-parameter model in fp16 that is roughly 140GB of memory traffic to produce a handful of characters. The arithmetic per byte read — the arithmetic intensity — is close to 1, while an H100's tensor cores want a ratio in the hundreds to stay busy.

So at batch size 1, a $30,000 accelerator spends nearly all its time waiting on memory. Its compute units are idle. You are not paying for FLOPs; you are paying for a very fast, very expensive memcpy.

💡 The Sentence the Whole Design Hangs On

Because those 140GB of weights are read regardless of batch size, running 64 sequences together costs almost exactly the same memory traffic as running one. The weights are read once and reused across every sequence in the batch. Batch size 64 is therefore close to 64× the throughput for roughly the same cost.

That single fact is why the scheduler is the most important component in this architecture, why the KV cache — which limits how many sequences fit in a batch — is the true bottleneck, and why an idle GPU is a catastrophe rather than an inefficiency.

Step 5 — The KV Cache

One more mechanism, and it is the one that turns an intractable problem into a merely expensive one.

Naively, generating token 401 means re-running attention over all 400 previous tokens — recomputing their keys and values from scratch, every single step. That is quadratic work and would make generation impossibly slow.

But because of the causal mask, the key and value vectors for a token never change once computed. Token 12's contribution is identical whether you are generating token 13 or token 400. So you compute them once and keep them: the KV cache. Each decode step then computes K and V for only the single newest token and appends to the cache.

This converts the per-step cost from quadratic to linear. It is not an optimisation — no production system works without it. And it comes with a bill:

KV Cache Memory · the number that caps your batch size bytes/token = 2 (K and V) × layers × kv_heads × head_dim × precision 70B-class model with grouped-query attention: 2 × 80 layers × 8 kv_heads × 128 head_dim × 2 bytes = ~320 KB / token 8,000-token conversation → ~2.5 GB of GPU memory, per user 8×H100 node → 640 GB HBM minus model weights → -140 GB available for KV cache → ~500 GB → ~200 concurrent conversations per node That is the batch size. Not CPU, not network — HBM.

Two hundred concurrent conversations per node, from a machine costing roughly a quarter of a million dollars. Now the fleet arithmetic from section 02 has a physical explanation, and the rest of this article is about pushing that number up.

07Deep Dive: Prefill, Decode & Continuous Batching

We established that batching is nearly free throughput. The obvious move is to collect requests into batches. The obvious implementation is also badly wrong, and watching a candidate discover why is one of the more satisfying moments in this interview.

Why Static Batching Fails

The naive approach: gather 32 requests, run them together, return all 32 results, repeat. This is how you would batch database writes, and it is how every batching system you have built before works.

It collapses here because generation lengths vary wildly. One user asks for a yes/no answer — 5 tokens. Another asks for an essay — 2,000 tokens. In a static batch, the 5-token request finishes almost immediately, and then its slot sits idle for the remaining 1,995 iterations while the batch waits for its slowest member. GPU utilisation falls off a cliff, and every short request pays the latency of the longest one in its batch.

Diagram 3 · Static vs Continuous Batching
Static batching pays for empty slots. Continuous batching refills them mid-flight — the single largest throughput win available.

Continuous Batching

The fix is to schedule at iteration granularity rather than request granularity. Because decode is already a loop of discrete steps, the scheduler can intervene between any two of them. After every step it evicts finished sequences, admits queued ones into the freed slots, and runs the next iteration with a different batch composition.

No request waits for another to finish. Utilisation stays near peak regardless of how wildly generation lengths vary. In practice this is a 2–4× throughput improvement over static batching on identical hardware — on our fleet, tens of thousands of GPUs' worth.

The Prefill/Decode Interference Problem

Now a subtler issue, and a good place to show depth. Prefill and decode want opposite things from the hardware, and they contend when mixed.

A prefill for a 1,500-token prompt is a large, compute-heavy operation. If you drop it into a batch of decode steps, every sequence already streaming stalls for the duration — users mid-sentence see their text visibly hitch. Prioritise decode instead and new requests queue behind them, pushing TTFT up.

Strategy How it works Trade-off
Chunked prefill Split a long prompt into fixed-size chunks, interleaving decode steps between them Smooth ITL, slightly higher TTFT. The usual default.
Disaggregated serving Separate GPU pools for prefill and decode; transfer the KV cache between them Each pool tuned for its bottleneck; costs a large cross-node transfer per request.
Prefill priority Always run waiting prefills first Best TTFT, visibly stuttering streams. Rarely worth it.

Disaggregation is what large deployments converge on, because it lets you buy different hardware for the two phases — compute-dense parts for prefill, bandwidth-dense parts for decode — and scale the pools independently against the 278M/74M tokens-per-second split we calculated earlier.

08Deep Dive: The KV Cache Is the Bottleneck

Batch size determines throughput. KV cache memory determines batch size. So the entire economics of this system reduce to one question: how many conversations can you keep resident in HBM at once?

The Fragmentation Problem

The naive allocator reserves, for each sequence, a contiguous block sized for the maximum possible context — say 8,000 tokens, 2.5GB. But the average conversation uses perhaps 1,500 tokens. You have reserved 2.5GB to use 470MB, and the waste is not recoverable because the block must stay contiguous in case the sequence grows.

This is textbook internal fragmentation, and measured on real workloads it wastes 60–80% of KV memory. That is the difference between 200 concurrent conversations per node and 50.

PagedAttention

The solution is the one operating systems reached for in the 1960s: virtual memory. Split the KV cache into fixed-size blocks (say 16 tokens each). Allocate blocks on demand as a sequence grows. Keep a per-sequence block table mapping logical positions to physical blocks, which need not be contiguous.

Paged KV Cache CONTIGUOUS (naive) seq A [################........................] reserved 8k, used 1.5k seq B [#####...................................] reserved 8k, used 0.9k └─ 70% of HBM reserved and idle ─┘ PAGED physical blocks: [b0][b1][b2][b3][b4][b5][b6][b7]... seq A block table: b0 → b3 → b7 (grows on demand) seq B block table: b1 → b2 free list: b4, b5, b6, ... (immediately reusable) waste = at most one partly-filled block per sequence (<4%) → 3-4× more concurrent sequences on identical hardware

Prefix Sharing — the Multiplier

Paging unlocks something better than efficiency. Because blocks are indirected through a table, two sequences can point at the same physical block.

This matters enormously given the actual traffic shape. Every request carries a system prompt — often hundreds of tokens, identical across millions of users. And in a multi-turn conversation, turn five re-sends the entire text of turns one through four. That shared prefix does not need to be recomputed or re-stored; it can be computed once and referenced by every sequence that shares it, copy-on-write at the point where they diverge.

💡 Why the Scheduler Must Be Cache-Aware

Prefix sharing only pays off if requests that share a prefix land on the same node, since KV blocks live in one machine's HBM. This turns routing from a load-balancing problem into a cache-affinity problem: route by hash of the conversation prefix, not round-robin.

A returning turn in an existing conversation then skips prefill for everything except the newest message — cutting TTFT from ~800ms to under 100ms and eliminating most of the prefill compute entirely. But affinity fights load balance: a hot prefix can overload one node. The honest answer is a hybrid — prefer the cache-owning node, fall back to least-loaded when it is saturated, and accept the recompute. Saying that trade-off out loud is a senior signal.

Eviction and Preemption

When memory runs out mid-generation — a batch of sequences all growing at once — something must give. Options, in increasing order of pain:

  • Stop admitting. Queue new requests; running ones continue. TTFT rises, ITL is unaffected. Always try this first.
  • Swap to host memory. Move a victim's KV blocks to CPU RAM over PCIe and bring them back later. Adds hundreds of milliseconds and burns PCIe bandwidth.
  • Preempt and recompute. Drop a victim's cache entirely and re-prefill it when rescheduled. Counterintuitively often cheaper than swapping, because prefill is fast and parallel while PCIe is not.

Which victim? Newest-first preserves the work already invested in long-running requests and avoids the pathological case where a nearly-complete 2,000-token generation is killed at token 1,900.

09Deep Dive: Streaming & Backpressure

Tokens are produced on a GPU deep inside the fleet and must reach a browser possibly on the other side of the planet, one at a time, for twenty seconds. Three problems fall out of that.

Connection Economics

At 555K messages/sec peak and ~12 seconds average generation, Little's Law gives the concurrency directly:

Little's Law · concurrent open connections L = λ × W = 555,000 req/s × 12s = ~6.7 million concurrent SSE streams Each is an idle-ish socket emitting ~20 small frames/second. → the streaming tier must be event-driven, not thread-per-request → ~65k connections/node ⇒ ~100+ dedicated edge nodes just to hold sockets → and every one of them is a stateful attachment to a specific GPU worker

This is why the streaming tier is worth separating from the API tier. It has a completely different resource profile — almost no CPU, enormous connection counts, long lifetimes — and mixing it with request/response traffic means sizing both for the worse case.

Cancellation Is a Cost Control

Users close tabs. They navigate away. They read the first sentence, decide it is wrong, and hit stop. In an ordinary web system an abandoned request is a rounding error. Here it is a GPU slot and 2.5GB of HBM, possibly for another fifteen seconds.

So disconnect detection must propagate all the way to the scheduler and free the slot immediately. This sounds obvious and is frequently missed: a naive implementation keeps generating into a dead socket, and at scale that wastes a meaningful fraction of the entire fleet. Treat client disconnect as a first-class cancellation signal, not an error path.

⚠️ The Resumability Trap

What happens if the network drops at token 300 of 400? The KV cache holding that generation lives in one GPU's memory and cannot be moved cheaply. Options: (a) discard and force a regenerate — simple, wastes the work, and the user gets different text because sampling is stochastic; (b) buffer emitted tokens in Redis keyed by request id, letting a reconnect replay from an offset while generation continues server-side. Option (b) costs a small write per token and is what makes "close your laptop, reopen it, the answer is still there" possible. Candidates who ask "what is the user experience on reconnect?" are thinking like product engineers, and it lands well.

10Deep Dive: Capacity, Cost & Routing

118,000 GPUs is the number you get by assuming every request goes to the biggest model. Nobody does that. The remaining levers are about serving as much traffic as possible on as little silicon as possible.

Model Tiering

The single largest saving is not a kernel optimisation — it is not calling the large model. Most traffic is short, simple, and perfectly well served by a model an order of magnitude cheaper. A router classifies the request and picks a tier, escalating only when needed.

Technique Mechanism Typical gain Cost
Model tiering Route easy prompts to a small model 5–10× on routed traffic Router mistakes degrade quality
Prefix caching Reuse KV for shared system prompts and prior turns Most prefill eliminated Forces cache-affinity routing
Quantization Serve weights at 8 or 4 bits instead of 16 2–4× memory, more batch Small, measurable quality loss
Speculative decoding A tiny draft model proposes several tokens; the big model verifies them in one pass 2–3× on ITL Wasted compute when drafts are rejected
Mixture of experts Activate only a few expert sub-networks per token Large model at small-model compute Memory holds ALL experts; routing imbalance

Speculative decoding deserves a sentence of explanation because it looks like magic. Since decode is memory-bandwidth-bound, verifying five candidate tokens costs almost exactly what verifying one costs — the weights are read either way. So a cheap draft model guesses ahead, the large model checks all the guesses in a single pass, and you keep the longest correct prefix. When the draft is good you get several tokens for the price of one; when it is wrong you have lost only the draft model's trivial compute.

Admission Control and Graceful Degradation

When demand exceeds a fixed GPU supply — and it will, because supply is fixed for months — something has to give. The failure you must avoid is uniform collapse, where everyone gets 4-second TTFT and the system looks broken to all 800M users simultaneously.

  • Shed by tier. Free users queue or fall back to the small model; paying users keep capacity. Degradation should be visible in the product, not in the latency graph.
  • Cap generation length under load. Fewer decode iterations per request directly increases request throughput.
  • Queue with a deadline. Reject fast when the queue implies a TTFT beyond what the user will tolerate — a quick honest error beats a 30-second spinner.
  • Never autoscale into a shortage. There is no elastic pool to burst into. Capacity planning here is procurement, not configuration.

Questions Worth Rehearsing

  • "Why can't you just add more servers?" — Because capacity is GPUs, supply is fixed for months, and an idle GPU costs the same as a busy one. The work is raising utilisation, not adding nodes.
  • "Why is the first token slow but the rest fast?" — Prefill processes the entire prompt in one compute-heavy pass; decode then reuses the KV cache and touches only one token per step.
  • "What limits how many users one GPU serves?" — HBM for the KV cache, not compute. Derive it: ~320KB/token × context length × concurrent sequences, against what remains after the model weights.
  • "How do you cut cost by half?" — Not one trick. Prefix caching removes most prefill, tiering removes most large-model calls, paging triples batch size, quantization doubles it again.
  • "What breaks first under 5× load?" — The scheduler queue. TTFT climbs while ITL stays flat, because running sequences are unaffected and new ones simply wait.
💡 Final Thought

Every other system in this series is about moving data around cheaply. This one is about renting the scarcest hardware on earth by the millisecond and refusing to let it idle. The candidates who do well are not the ones who can name the most inference frameworks — they are the ones who can say "decode is memory-bandwidth-bound, so batching is nearly free, so the KV cache is what actually limits us, so let's talk about how memory is allocated" and follow that chain without stopping. Everything in this design is downstream of one number: how many conversations fit in HBM.
